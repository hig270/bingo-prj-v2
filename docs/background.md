# 背景: 旧実装の調査結果

旧リポジトリ `hig270/syshack-bingo`（最新コミット `be62b46`）を調べた結果のまとめ。作り直しの判断材料として残す。

## 旧実装の構成
- Next.js 15 (App Router) + TypeScript + Shadcn UI + Tailwind v4
- Firebase Firestore（`onSnapshot` でリアルタイム更新）。API ルートでもクライアント SDK を使っていた
- 設計メモ: リポジトリ直下の `database.txt`、`directory.txt`、`document.txt`

## 旧実装のゲーム設定（特殊モードの相談の材料）
- モード選択: スピード（3×3 のカード）／普通／カスタム（確率操作などの独自ルール）。実装済みは普通のみ
- 設定項目（`customs`）:
  - `winLine`: 景品獲得に必要なビンゴ数（1〜3）
  - `highSpeed`: 9マスビンゴ
  - `reverse`: 逆ビンゴ
  - `changeProbability`: 確率操作モード（false | light | medium | heavy）
  - `rareNumber`: レアナンバーモード
- 引き継ぐ候補として挙がっているもの: 確率表示、ランキング、特殊モード（9マス・逆ビンゴ・レアナンバー・確率操作）

## 旧実装の画面
トップ → モード選択 → ゲーム設定 → ホストの募集画面（QR コード・参加者一覧）→ ホストのゲーム画面 → 結果画面。プレイヤーは参加画面 → 待機画面 → ゲーム画面。新設計での変更点は [screens.md](screens.md) に反映済み。

## 問題点

### Firestore の読み書きが人数に比例して膨らむ
N = プレイヤー数として、1回の抽選あたり概算 4N 回以上の読み書きが発生していた。100人 × 75回抽選で約3万回となり、無料枠を超えた。

- ホストの抽選: ルームを読む → 抽選番号を書く → 全プレイヤーを読む（N）→ 全員の順位を書く（N）
- 各プレイヤーの判定: プレイヤーとルームを読む → 進捗を書く（抽選ごとに N 回）
- ランキング取得: 全プレイヤーを読む（N）＋ 各プレイヤーの補足情報を個別に読む（N）

### ポイント制ランキングの問題（`src/app/api/gameroom/player/playing/route.ts`）
旧実装の計算式:

| 要素 | 点数 |
|---|---|
| 開いているマスの数（FREE を含む） | 1マス1点 |
| ビンゴしたライン（5/5） | 1ラインごとに +10 |
| リーチのライン（4/5） | 1ラインごとに +5 |
| 3/5 のライン | +2 のつもりが、バグで 0点 |
| 2/5 のライン | 1ラインごとに +1 |
| 四隅と斜めの内側の計8マス | 開いていれば1マスごとに +2 |

問題:
- `else if (sum === 3 && missingNumbers.length === 2)` が常に成り立ち、+2 の分岐に届かない。ラインを 2/5 → 3/5 に進めると差し引き ±0 になる
- 点の段階（1, 2, 5, 10）に根拠がない
- 斜めのマスは関わるライン数が多いうえにボーナスも乗り、二重に優遇される
- ポイントの高さがビンゴへの近さと一致しない（待ちの種類数を区別できない、など）
- 序盤と終盤で効く要素が変わる
- ホスト画面（景品獲得者を除く）とプレイヤー画面（全員）で順位の母集団が違う
- 同点の扱いが未定義
- 順位の計算が抽選の直後に走るため、常に1抽選分遅れる（`setTimeout` による遅延実行もサーバーレスでは保証されない）
- 5×5 に固定されており、特殊モードに対応できない

→ 新設計では「景品獲得ラインに達するまでの期待抽選回数」に置き換える（[decisions.md](decisions.md)）。

### 確率表示（旧実装）
- ビンゴ確率 = リーチのラインを完成させる番号の種類数 ÷ 残りの番号数
- リーチ確率 = 3/5 のラインに含まれる未抽選番号の種類数 ÷ 残りの番号数
- どちらも「次の1回の抽選で」の確率。変数名 `reachTargetNumbers` と `bingoTargetNumbers` の中身が逆になっていた

### その他
- 中央マスは番号 `100` で FREE を表現していた
- 当選番号を即座に強調表示し、離席時は自動で開けていた → ユーザーから「探す楽しさがない」「違和感がある」との意見
- 仕様メモにあった「景品の残り人数の表示」「開始確認ダイアログ」は未実装だった
- 抽選履歴の表示がホスト・プレイヤーとも無かった
- プレイヤーは結果画面に自動遷移しなかった

## 検証: 期待抽選回数で角・斜めのマスが優遇されるか

FREE 以外に1マスだけ開いた状態で、ビンゴまでの期待抽選回数（小さいほど有利）を計算した。

| 開いたマス | 期待抽選回数 |
|---|---|
| FREE のみ | 41.37 回 |
| 角 | 38.92 回 |
| 斜めの内側 | 38.92 回 |
| 中央の行・列上のマス | 39.29 回 |
| その他の辺のマス | 39.99 回 |

旧実装がボーナス点で表そうとしていた「角・斜めのマスの有利さ」が、確率計算から自然に出てくることを確認した。計算は、12本のラインの組み合わせ（4096通り）に包除原理を使い、厳密に行った。
