# 技術構成のメモ

決定事項は [decisions.md](decisions.md) が正。このファイルは、技術構成の説明、比較の経緯、実装前に確認すること、未採用の設計案をまとめたもの。

## 全体像（決定済みの構成）

```
                 ┌────────────── Cloudflare ──────────────┐
 プレイヤー端末 ─┐ │                                        │
 プレイヤー端末 ─┼─┼─▶ Worker ──(ルームIDで振り分け)──▶ RoomDO（ルームA）
 ホスト画面   ─┘ │    ├ 画面ファイル（SPA）の配信          ├ メモリ上の状態
                 │    └ API（ルーム作成など）              ├ 保存領域（キーと値の API）
                 │                                        └ WebSocket × 最大1000本程度
                 │                           RoomDO（ルームB）…
                 └────────────────────────────────────────┘
```

### Cloudflare Workers
- 世界中の Cloudflare の拠点で動くサーバーレス実行環境。起動が速く、コールドスタートをほぼ気にしなくてよい。
- 画面（SPA）のファイル配信と API を1つの Worker で担当できる。
- それ自体は状態を持たない。

### Durable Objects
- 「ID ごとに世界で1つだけ存在する、状態を持てるオブジェクト」。TypeScript のクラスとして書く。
- 同じ ID 宛てのリクエストは必ず同じインスタンスに届き、**処理は1つずつ順番に実行される**。ロックや競合対策が不要。
  - タップの検証、どの抽選回でビンゴしたかの記録、順位決定ゲームなど、順番が大事な処理に向く。
- インスタンスごとに保存領域を持つ。内部は SQLite だが、キーと値の API を使えば SQL や列の型に触れない（値は JavaScript の値のまま保存される）。
- 最初にアクセスした場所の近くに作られる。
- アラーム（「○秒後に処理を実行」）が使える。ゲーム終了後の片付けなどに使える。

### WebSocket Hibernation
- 抽選の合間など、操作がない間は WebSocket の接続を保ったままメモリから退避でき、実行時間の課金がほぼかからない。
- **復帰時にメモリ上の変数は消えている**。抽選番号・開けたマスなどの状態は変更のたびに保存し、復帰時に読み戻す。各接続には「どのプレイヤーの接続か」の情報を付けておける。

### 開発
- Wrangler（公式 CLI）。`wrangler dev` で Durable Objects を含めて手元で動かせる。`wrangler deploy` でデプロイ。
- Vitest 用の公式ツールで Durable Objects を含むテストが書ける。
- ユーザーは Cloudflare 管理の個人ドメインを持っており、そのまま割り当てられる。

## 試算と性能

- 試算条件: 300人・抽選75回・1人約25タップ・1ゲーム約40分
- Cloudflare の課金: 新規接続は1リクエスト、受信メッセージは20通で1リクエスト換算、**送信は無料**
  - 1ゲーム ≒ 接続300 ＋ タップ7,500通 ÷ 20 ≒ 約700リクエスト
- 1つの Durable Object の処理能力の目安は毎秒約1000リクエスト（ソフトリミット）。1000人が抽選直後に一斉にタップしても毎秒200件程度。
- 一番重い処理は、タップのたびの期待抽選回数の計算（ラインの組み合わせ 4096 通りの包除原理）。1000人分でも合計1〜2秒程度の見込み。負荷試験で確認し、遅ければランキング更新を0.5秒ごとにまとめるなどで調整する。

## 未採用の設計案（叩き台）

以下は相談の中で出た Claude の提案で、まだ決定していない。

- **カードの生成**: シード（roomId ＋ playerId など）から決定的に生成すれば、カード自体を保存しなくてよい（旧メモからの案）
- **確率の計算場所**: タップは毎回サーバーに送るので、確率 A〜H はサーバーで計算してタップへの応答として返せる。端末側に残るのはカード表示と開け忘れの判定（端末が持つ抽選番号・カード・開けたマスで完結）程度
- **ホスト画面へのランキング送信**: 0.5秒ごとなどにまとめて送り、負荷を抑える
- **保存の層**: キーと値の API を Zod などのスキーマ検証で包む（方針は決定済み、ライブラリは未決定）
- **モノレポの構成**: `apps/web`（フロントエンド）、`apps/server`（Worker ＋ RoomDO）、`packages/game`（Cloudflare に依存しないゲームロジック）

## 比較の経緯（基盤選定）

「ルームの状態を1か所で順番に処理できるか」「数百人への一斉配信」「待機中の費用」「運用の手間」「特定サービスへの依存」で比較した。

| 候補 | 評価 |
|---|---|
| **Cloudflare Workers + Durable Objects** | 採用。要件にそのまま合う。依存はゲームロジックの独立で緩和する |
| Fly.io などの常駐サーバー（Node / Go / Elixir） | 次点。設計はきれいに作れるが、固定費と運用が必要。複数台にするとルームごとの振り分けが必要 |
| Go + Fly.io + PostgreSQL | 型の堅さでは有利。デプロイや再起動でメモリ上の状態が消えるため保存と復元の作りが必要 |
| AWS サーバーレス（AppSync Events / API Gateway WebSocket + Lambda + DynamoDB） | 費用は安い（1ゲーム約 $0.04）が、状態を持たないため DB での競合対策が必要でロジックが複雑になる。選ぶなら API Gateway より AppSync Events |
| AWS コンテナ（ECS Fargate など） | ロードバランサー込みで固定費が高く、この規模には大がかり |
| 配信専門サービス（Ably・Pusher・Supabase Realtime） | ロジック用のサーバーが別に必要。無料プランは同時接続数の上限が厳しいことが多い |
| Firebase 継続 | 全員が同じドキュメントを購読すると読み取りが人数×抽選回数で増える |
| Rails（Action Cable）・Django（Channels） | ログインや管理画面などの CRUD が得意な一方、このアプリの中心はリアルタイム処理。ルームの状態を DB や Redis に置いてロックが必要になる |

言語は「基盤の選択とほぼ同じ」（Durable Objects で動くのは実質 JavaScript / TypeScript）という整理のうえで TypeScript に決めた。

### SQLite について
ユーザーは「型が甘すぎる」ことを理由に SQLite を避けたい。Durable Objects の保存領域の内部が SQLite であることは避けられないが、キーと値の API を使えば列の型の影響を受けない。他に検討した対策は STRICT テーブル（列の型を厳密に強制する。Durable Objects で使えるかは未確認）と Drizzle ORM。
