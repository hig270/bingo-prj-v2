# 技術構成のメモ

決定事項は [decisions.md](decisions.md) が正。このファイルは、技術構成の説明、比較の経緯、実装前に確認すること、未採用の設計案をまとめたもの。

## 全体像（決定済みの構成）

```
 プレイヤー端末 ─┐
 プレイヤー端末 ─┼──▶ Cloudflare
 ホスト画面     ─┘     │
                       ├─ 静的アセット配信: 画面ファイル（SPA）。Worker を通さない
                       │
                       └─ Worker（Hono）: API（ルーム作成・参加など）と WebSocket の受け付け
                             │  ルームIDで振り分け（RPC。WebSocket の接続開始だけ fetch）
                             ▼
                          RoomDO（ルームA）
                             ├ メモリ上の状態
                             ├ 保存領域（キーと値の API）
                             └ WebSocket × 最大1000本程度
                          RoomDO（ルームB）…
```

### Cloudflare Workers
- 世界中の Cloudflare の拠点で動くサーバーレス実行環境。起動が速く、コールドスタートをほぼ気にしなくてよい。
- 画面（SPA）のファイル配信と API を1つの Worker で担当できる。再接続用のトークンを HttpOnly Cookie で扱うため、画面と API・WebSocket は同じサイトで配信する（決定済み）。
- それ自体は状態を持たない。

### Durable Objects
- 「ID ごとに世界で1つだけ存在する、状態を持てるオブジェクト」。TypeScript のクラスとして書く。
- 同じ ID 宛てのリクエストは必ず同じインスタンスに届き、**処理は1つずつ順番に実行される**。ロックや競合対策が不要。
  - タップの検証、どの抽選回でビンゴしたかの記録、順位決定ゲームなど、順番が大事な処理に向く。
- インスタンスごとに保存領域を持つ。内部は SQLite だが、キーと値の API を使えば SQL や列の型に触れない（値は JavaScript の値のまま保存される）。
- 最初にアクセスした場所の近くに作られる。
- アラーム（「○秒後に処理を実行」）が使える。ゲーム終了後の片付けなどに使える。

### WebSocket Hibernation
- 抽選の合間など、操作がない間は WebSocket の接続を保ったままメモリから退避でき、実行時間の課金がほぼかからない。
- **復帰時にメモリ上の変数は消えている**。抽選番号・開けたマスなどの状態は変更のたびに保存し、復帰時に読み戻す。各接続には「どのプレイヤーの接続か」の情報を付けておける。

### 開発
- 技術選定の決定事項（React・TanStack Router・Zustand・Hono・Zod・pnpm・ESLint・Prettier・Vitest・TypeScript 6 など）は decisions.md の「技術スタック・基盤」「型安全の方針」を参照。
- Wrangler（公式 CLI）。`wrangler dev` で Durable Objects を含めて手元で動かせる。`wrangler deploy` でデプロイ。
- Vitest 用の公式ツール（@cloudflare/vitest-plugin）で Durable Objects を含むテストが書ける。
- ユーザーは Cloudflare 管理の個人ドメインを持っており、そのまま割り当てられる。

## 試算と性能

- 試算条件: 300人・抽選75回・1人約25タップ・1ゲーム約40分
- Cloudflare の課金: 新規接続は1リクエスト、受信メッセージは20通で1リクエスト換算、**送信は無料**
  - 1ゲーム ≒ 接続300 ＋ タップ7,500通 ÷ 20 ≒ 約700リクエスト
- 1つの Durable Object の処理能力の目安は毎秒約1000リクエスト（ソフトリミット）。1000人が抽選直後に一斉にタップしても毎秒200件程度。
- 一番重い処理は、タップのたびの期待抽選回数の計算（ラインの組み合わせ 4096 通りの包除原理）。1000人分でも合計1〜2秒程度の見込み。負荷試験で確認し、遅ければランキング更新を0.5秒ごとにまとめるなどで調整する。

## 実装前に確認すること（2026-11-12 に公式ドキュメントで確認済み）

数値は変わりうるので、根拠にするときは再確認する。

- [x] **Durable Objects の料金**（Workers 有料プラン。https://developers.cloudflare.com/durable-objects/platform/pricing/ ）
  - リクエスト: 月100万まで含まれる。超過は100万あたり $0.15。HTTP・RPC・WebSocket の受信メッセージ・アラームが対象。受信メッセージは20通で1リクエスト換算、接続の開始は1リクエスト。**送信メッセージは課金されない**。
  - 実行時間: 月40万 GB-s まで含まれる。超過は100万 GB-s あたり $12.50。1つの Durable Object に割り当てられる128MB で計算される。**Hibernation 中は課金されない**。
  - SQLite 方式の保存: 読み取り行数は月250億行、書き込み行数は月5,000万行、保存量は5GB・月まで含まれる。超過は書き込み100万行あたり $1.00 など。2026年1月7日から課金開始。
  - 試算への当てはめ（300人・1ゲーム40分）: リクエスト約700。実行時間は40分間ずっと起きていても 0.125GB × 2,400秒 = 300 GB-s。書き込みはタップごとに保存して約7,500行。いずれも含まれる量に比べて十分小さい（ポートフォリオサイトと共有でも問題になりにくい）。
- [x] **1つの Durable Object あたりの WebSocket 同時接続数の上限**（https://developers.cloudflare.com/durable-objects/platform/limits/ 、https://developers.cloudflare.com/durable-objects/best-practices/websockets/ ）
  - 公式の制限一覧に**上限の記載はない**。「1つのインスタンスで数千のクライアントをつなげる」という記述のみ。非公式のミラーに「32,768」という値があるが、公式では確認できなかった。
  - 実際の上限は CPU とメモリ（128MB）で決まる。設計目標の1000人は負荷試験で確認する。
  - 関連する制限: 1つの Durable Object あたり毎秒1,000リクエストのソフトリミット（超えると overloaded エラー）。受信メッセージの大きさは最大32MiB。1回の処理の CPU 時間は既定30秒。
- [x] **キーと値の API の条件**（https://developers.cloudflare.com/durable-objects/api/storage-api/ ）
  - SQLite 方式の Durable Object で使える。非同期の `ctx.storage.get/put/delete/list` と、同期の `ctx.storage.kv` の2種類がある。
  - 値は structured clone で扱える型（ほとんどの JavaScript の値）。キーと値の合計は最大 8MB。1つの Durable Object の保存量は最大 10GB。
  - 非同期の `get/put/delete` は1回で最大128キーをまとめて扱える。
- [x] **旧来のキーと値だけの保存方式**
  - 有料プランでも、すでにその方式を使っているアカウントでしか新しく作れない。公式は SQLite 方式を推奨。今回は SQLite 方式（＋キーと値の API）を使うので影響はない。
- [x] **休止できる方式（Hibernation）の接続を、サーバーから切ったときの知らせ**（2026-11-16 に手元の実行環境（wrangler dev・Vite の開発サーバー）で確認）
  - `ctx.acceptWebSocket` で受け付けた接続を、`webSocketMessage` の外（接続を受け付けた直後、別の接続のメッセージの処理の中、`setTimeout` の中）で `close(code, reason)` しても、**画面（ブラウザ・Node の WebSocket）に close が届かなかった**。その接続自身からメッセージが来たときに `close` した場合と、休止しない方式（`accept()`）の場合は届いた。Vitest（`@cloudflare/vitest-plugin`）の中では届く。
  - 本番でも同じかは未確認。どちらでも動くよう、**切る直前に理由を `bye` メッセージで送り、画面はそれを受け取ったら自分から切る**作りにした（close コードは予備として残す）。外した人の接続から後で届いたメッセージも、サーバーで受け付けない。
  - **原因の調査**（2026-11-18。workerd 1.20261110.1・wrangler 4.160.1。実験用の小さな Worker と、WebSocket のフレームを生で読むクライアントで確かめた）:
    - サーバーは **close フレーム（code・reason）を送っている**。届いていないのは、その後の **TCP の切断**。クライアントが close フレームを返し、サーバーの `webSocketClose` が呼ばれて `close()` も例外なく通るのに、TCP が閉じない。
    - ブラウザ・Node の WebSocket は、close フレームの受け取りではなく **TCP が閉じたときに close のイベントを出す**ので、画面からは「close が届かない」ように見える。
    - TCP は、Durable Object が何もしなくなってから約 10 秒後（休止するとき）に閉じた。その間に他の接続からメッセージが届き続けると、閉じない。
    - その接続自身のメッセージの処理中に `close()` した場合だけは、クライアントが close フレームを返した直後に TCP が閉じる。
    - wrangler の中継（ProxyWorker）を通さず workerd に直接つないでも同じ。互換性の日付（2024-01-01・2026-11-10）でも変わらない。Vitest で届くのは、テストのクライアントが workerd の中の WebSocket で、TCP を使わないため。
    - **既知の不具合だった**（2026-11-18 に GitHub で確認）: [workerd#7566](https://github.com/cloudflare/workerd/issues/7566)（2026-09-29 報告）と [workerd#8185](https://github.com/cloudflare/workerd/issues/8185)（2026-11-03 報告）。どちらも未解決で、開発者の反応はまだない。条件は「**クライアントがその接続でデータのフレームを1つも送っていないうちに、サーバーから切る**」こと。#7566 のコメントによると、約 10 秒は Durable Object がメモリから外れるまでの時間で、忙しい間はずっと閉じない。直す変更（PR）もまだない。
    - 追加で確かめたこと（既存の報告に書かれていない点）: 先にクライアントが1回でも送っていれば、すぐ閉じる。送ったものが、ルームを起こさずに返す自動応答の `"ping"`（`setWebSocketAutoResponse`）でも同じ。ルームが忙しい（`setInterval` が動いている）間でも同じ。何も送っていなければ、忙しい間は 20 秒たっても閉じない。
    - このアプリへの影響と回避策: `bye` で先に理由を伝えているので、画面の動きには影響しない（TCP の接続が残るだけ）。そのうえで、画面は**つないだ直後に `"ping"` を1回送る**（その後は 30 秒ごと）ことで、この不具合に当たらないようにした（2026-11-18。`api/socket.ts`）。自動応答で返すので、ルームは起こさない。
    - **本番でも同じ**（2026-11-18 に、実験用の Worker を workers.dev にデプロイして確認し、確認後に削除した。互換性の日付 2026-11-10）。サーバーの close フレームから TCP の切断までの時間は、次のとおり。何も送っていない接続は約 10 秒（3 回とも）、ルームが忙しいと 60 秒たっても閉じない（2 回とも）。先に `"ping"`（自動応答）か普通のメッセージを送っていれば 11〜20 ミリ秒。その接続自身のメッセージの処理中に切った場合と、休止しない方式（`accept()`）も 12〜20 ミリ秒。Node の WebSocket の close のイベントも、何も送っていない接続では約 10 秒遅れ、ルームが忙しいと 70 秒たっても出なかった。本番で確かめた報告は、それまで無かった。本番の結果と追加で確かめたことを、2026-11-18 に [workerd#7566 へのコメント](https://github.com/cloudflare/workerd/issues/7566#issuecomment-6956993144) で報告した（クライアントから切る場合の本番の測定は [workerd#8426](https://github.com/cloudflare/workerd/issues/8426) にある）。
    - 作りへの影響: `bye` を受け取ったら画面が自分で後片付けする今の作りで、本番がどちらでも動く。画面は close のイベントを待たずに次の処理へ進む（`api/socket.ts`）。
- [x] **Hibernation の注意点**（https://developers.cloudflare.com/durable-objects/best-practices/websockets/ ）
  - 各接続に付けられる情報（`serializeAttachment`）は最大 16,384 バイト。プレイヤー ID 程度を付け、詳しい状態は保存領域に置く。
  - `setTimeout` / `setInterval`、実行中のアラーム、外向きの WebSocket は Hibernation を妨げる。予約しただけのアラームは妨げない（公式の資料は、アラームの実行などのイベントが休止を妨げると書き、休止中のルームはアラームで起き直すとしている。2026-11-18 に確認。decisions.md「ルームのデータを消す時期」）。ランキング送信を「0.5秒ごと」にまとめる案は、この点を考慮して作り方を決める。
  - WebSocket の ping には実行環境が自動で応答し、Durable Object は起こされない。

## 実装時の方針（速さ・通信量）

決定事項ではなく作り方の指針。実装しながら調整する。負担がかかるのは主に「最初の読み込み（数百人が QR を読んだ瞬間）」「再接続の殺到」「タップごとの確率計算」「ホストへのランキング送信」で、WebSocket のメッセージ自体は小さい。

### 最初の読み込み
- 画面ファイルは Worker を通さず静的アセット配信で返す（料金なし・回数上限なし。2026-11 に公式で確認）。Worker を動かすのは API と WebSocket だけにする。そのため URL は、画面（`/r/<ルームID>`）と API・WebSocket（例: `/r/<ルームID>/api/...`、`/r/<ルームID>/ws`）をパターンで見分けられるようにする（Cookie の `Path=/r/<ルームID>` と両立）。
- 日本語の Web フォントは使わない（端末のフォントを使う）。使うなら必要な文字だけに絞る。
- 画面ごとにファイルを分ける（プレイヤーにホスト画面のコードを読み込ませない。TanStack Router の自動分割）。
- Vite のハッシュ付きファイル名で長期キャッシュする。
- 画像は SVG。軽い動き（UI の切り替えなど）は CSS の `transform` / `opacity` で書く。派手な演出の作り方は別に決める。

### 通信
- 接続・再接続のときだけ全体（スナップショット）を送り、その後は差分を送る。各メッセージに通し番号を付け、端末が抜けに気づいたら全体を取り直す。
- 再接続は指数バックオフ＋ジッター（人ごとにランダムにずらす）で、1000人が同時に押し寄せるのを防ぐ。
- ゲーム中は Screen Wake Lock API で画面を消さない（画面が消えると iPhone では WebSocket が切れて再接続が多発するため）。
- ホストに送るランキングは、表示する行だけを、変化があったときに0.5秒程度まとめて送る。`setInterval` は休止を止めるので使わず、「タップが来たときに前回の送信から0.5秒たっていれば送る」形にする。
- 開けたマスは25ビットの整数で表す（通信・保存とも小さく、判定も速い）。
- メッセージは JSON のまま（MessagePack などは、メッセージが小さく効果がないので使わない）。
- ルームの Durable Object は、作成時に location hint でアジア太平洋を指定する。

### 計算
- 「特定の k 個のマスが残りの抽選のうちに全部出る確率」は残りの番号数と k だけで決まり全員に共通なので、抽選のたびに k = 0〜25 の表を1回作り、全員のタップで使い回す。
- ライン判定は、各ラインを25ビットのマスクで表してビット演算で行う。

### 保存
- プレイヤーごとに別のキーで保存する（1人のタップで全員分を書き直さない）。
- 確率や順位など計算で出せる値は保存しない。

## 未採用の設計案（叩き台）

以下は相談の中で出た Claude の提案で、まだ決定していない。

- **確率の計算場所**: タップは毎回サーバーに送るので、確率 A〜H はサーバーで計算してタップへの応答として返せる。端末側に残るのはカード表示と開け忘れの判定（端末が持つ抽選番号・カード・開けたマスで完結）程度
- **ホスト画面へのランキング送信**: 0.5秒ごとなどにまとめて送り、負荷を抑える
- **モノレポの構成**: `apps/web`（フロントエンド）、`apps/server`（Worker ＋ RoomDO）、`packages/game`（Cloudflare に依存しないゲームロジック）

## 比較の経緯（基盤選定）

「ルームの状態を1か所で順番に処理できるか」「数百人への一斉配信」「待機中の費用」「運用の手間」「特定サービスへの依存」で比較した。

| 候補 | 評価 |
|---|---|
| **Cloudflare Workers + Durable Objects** | 採用。要件にそのまま合う。依存はゲームロジックの独立で緩和する |
| Fly.io などの常駐サーバー（Node / Go / Elixir） | 次点。設計はきれいに作れるが、固定費と運用が必要。複数台にするとルームごとの振り分けが必要 |
| Go + Fly.io + PostgreSQL | 型の堅さでは有利。デプロイや再起動でメモリ上の状態が消えるため保存と復元の作りが必要 |
| AWS サーバーレス（AppSync Events / API Gateway WebSocket + Lambda + DynamoDB） | 費用は安い（1ゲーム約 $0.04）が、状態を持たないため DB での競合対策が必要でロジックが複雑になる。選ぶなら API Gateway より AppSync Events |
| AWS コンテナ（ECS Fargate など） | ロードバランサー込みで固定費が高く、この規模には大がかり |
| 配信専門サービス（Ably・Pusher・Supabase Realtime） | ロジック用のサーバーが別に必要。無料プランは同時接続数の上限が厳しいことが多い |
| Firebase 継続 | 全員が同じドキュメントを購読すると読み取りが人数×抽選回数で増える |
| Rails（Action Cable）・Django（Channels） | ログインや管理画面などの CRUD が得意な一方、このアプリの中心はリアルタイム処理。ルームの状態を DB や Redis に置いてロックが必要になる |

言語は「基盤の選択とほぼ同じ」（Durable Objects で動くのは実質 JavaScript / TypeScript）という整理のうえで TypeScript に決めた。

### SQLite について
ユーザーは「型が甘すぎる」ことを理由に SQLite を避けたい。Durable Objects の保存領域の内部が SQLite であることは避けられないが、キーと値の API を使えば列の型の影響を受けない。他に検討した対策は STRICT テーブル（列の型を厳密に強制する。Durable Objects で使えるかは未確認）と Drizzle ORM。
