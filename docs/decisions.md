# Bingo!2 作り直し — 決定事項ログ

旧リポジトリ: `hig270/syshack-bingo`（Next.js + Firestore）。本リポジトリで完全に作り直す。

## 目的（必須要件）

- 抽選結果のリアルタイム共有
- 確率のリアルタイム表示
- ビンゴカードのリアルタイム共有（ホスト画面での表示用）
- 数百人規模の参加に耐える

## 決定事項

### マスの開け方・押し忘れ
- マスはプレイヤーの手動操作でのみ開く。**自動オープン・自動強調表示はしない**。
  - 背景: 旧実装では当選番号を即座に強調表示し、離席時は自動で開けていたが、ユーザーから「紙のビンゴにあった探す楽しさが失われる」「自動で開くのは違和感がある」との意見があった。
- 抽選済みでない番号のタップはサーバーが受け付けない。

### 押し忘れ対策（キャラクターの吹き出し）
- 画面左上にキャラクターを置く。
- 普段はタップすると画面上部に吹き出しが出て何か喋る（数秒で消える）。
- 抽選番号がカードにあったのに開けないまま次の抽選が始まったら、キャラクターが「開け忘れがあるかも」などと吹き出しで知らせる。
  - 吹き出しは**開け忘れがある限り表示し続ける**（数秒で消えない）。開け忘れがなくなったら消える。
  - ヒントの詳しさは段階的に上げない（個数や場所は教えない）。
  - 開け忘れの吹き出しが出ている間は、キャラクターをタップしても何も起こらない。
- リーチ・ビンゴ・順位決定ゲームの開始などの演出も、まずはキャラクターの吹き出しで行う（派手な演出は後で検討）。
- キャラクターのデザインは未作成。当面は仮の図形で実装し、後でオリジナルのキャラクターに差し替える。
- 判定は端末内で完結する（抽選済み番号・自分のカード・開けたマスはすべて端末が持っている）。
- 方針: 「ユーザーの操作がトリガー」。システムが勝手に開けたり、場所を教えたりしない。
- 検討して採らなかった案: 当選マスの強調表示、時間差の自動オープン、段階的に詳しくなるヒント（行や列を示すなど）、本人が押すヒントボタン。
- 出た番号の一覧（抽選履歴）はヒントではなく基本機能として扱う（ホスト画面に常時表示、プレイヤーはメニューから確認。詳細は「画面構成」）。

### ビンゴ判定
- ラインの最後のマスを押した瞬間に自動でビンゴ成立とする（申告ボタンは設けない）。
- 抽選番号上ではビンゴしていても、押していなければ押すまでビンゴとして扱わない。

### 確率表示・ランキング
- プレイヤーに見せる確率は、**プレイヤーが開けたマス**をもとに計算する。
- ホスト画面のランキングも**プレイヤーが開けた情報**をもとにし、タップ時に変動する。
- → タップは都度サーバーへ送信し、サーバー側で検証・集計する。

### ランキングの指標
- 旧実装のポイント制（開けたマス数＋ライン進捗点＋特定8マスボーナス）は**廃止**する。
  - 理由: 重み付けに根拠がない／ラインを 2/5→3/5 に進めても点が増えないバグ／ポイントの高さがビンゴへの近さと一致しない／5×5 固定で特殊モードに対応できない。
- 未達成者は**景品獲得ラインに達するまでの期待抽選回数**（あと平均何回の抽選で達するか）の小さい順に並べる。
  - 開けたマスを基準に計算する。見落としのマスは「まだ抽選されていない」ものとして扱う（実際の抽選状況を使うと見落としの存在が漏れるため）。
  - 角・斜めのマス、FREE を含むラインのマスの有利さは、確率計算から自然に反映される（検証済み）。
  - 計算はラインの組み合わせの包除原理で厳密に行う。タップのたびに、その人の分だけ再計算する。
  - 下位表示は期待抽選回数が最も大きい人たち。
- 期待抽選回数が同じ人は**同順位**とする。
- 検討して採らなかった案: 開けたマスの数、リーチ状況の辞書式比較、ポイント制の修正版。期待抽選回数は「重みがない」「会場に説明しやすい（あと平均○回）」「待ちの種類数も反映される」「特殊モードにもラインの定義を差し替えるだけで使える」ことから選んだ。

### プレイヤー画面の確率・状況表示
- 当面は以下をすべて表示する（見せ方の取捨選択は後で検討）。
  - A. 景品獲得ラインに達するまでの期待抽選回数（ランキングと同じ値）
  - B. 次の抽選でビンゴ（ライン1本の完成）する確率
  - C. 5回以内にビンゴ（ライン1本の完成）する確率
  - D. 順位（例: #12 / 300人）
  - E. 景品獲得ラインの進み具合（例: ビンゴ 1 / 2）
  - F. 次の抽選番号が自分のカードのどこかに当たる確率
  - G. 次の抽選で景品獲得ラインに達する確率（景品獲得ラインが2本以上のときのみ）
  - H. 5回以内に景品獲得ラインに達する確率（景品獲得ラインが2本以上のときのみ）
- B・C の「ビンゴ」はライン1本の完成を指す。すでに1本以上ビンゴしている場合は、まだ完成していない**新しいライン**の完成を指す。
- 景品獲得ラインが1本のときは B=G、C=H なので G・H は表示しない。
- いずれも開けたマスを基準に計算する。分母（残りの番号数）は実際の残り番号数を使う。
  - 見落としが多いと、未開封マス数が残り番号数を超えて確率が 100% を超えうる（見落としがあるときだけ起きる）。その場合は 100% で頭打ちにする。

### 技術スタック・基盤
- 言語は**フロントエンド・バックエンドとも TypeScript**。
- 基盤は **Cloudflare Workers + Durable Objects**（1ルーム＝1つの Durable Object、WebSocket Hibernation を使用）。
  - 比較した候補: AWS（API Gateway / AppSync Events + Lambda + DynamoDB、ECS）、Go + Fly.io + PostgreSQL、Elixir/Phoenix、Django、配信専門サービス（Ably・Pusher・Supabase Realtime）。
  - 選定理由: ルームの状態を1か所で順番に処理できる、数百人への一斉配信の送信が無料、待機中の費用がほぼゼロ、運用の手間が少ない。
- ゲームロジック（カード生成・判定・確率計算・順位決定）は Cloudflare に依存しない独立したモジュールにする（将来の移行に備える）。
- フロントエンドは **React（＋ Vite）の SPA** とし、Worker の静的アセット配信で出す。SSR（Next.js など）は使わない。
  - 理由: 画面（TSX）まで TypeScript 本体で型チェックできる（Svelte・Vue は専用ツールでのチェックになる）、旧実装で経験がある、周辺ライブラリと情報が最も多い。
  - 頻繁な更新（ランキング・確率）は、状態を1か所に置いて各部品が必要な部分だけを購読する作りで対応する。
  - 検討して採らなかった案: Solid（型安全と更新の速さは優れるが、props の分割代入で更新が止まるなどの落とし穴が型で検出できない、周辺ライブラリが少ない）、Svelte 5・Vue 3（テンプレートの型チェックが専用ツール頼み）、Preact（React 向けライブラリの互換に時々問題）、Angular（この用途には大がかり）。
- フロントエンドの周辺ライブラリ:
  - ルーティングは **TanStack Router**（URL のパラメータや画面間のリンクが型でチェックされる）。URL は「トップ」「ルーム作成」「ホスト画面」「プレイヤー画面」程度で、募集→ゲーム→結果の切り替えは URL ではなくサーバーから届くルームの状態で決める。
  - HTTP のデータ取得ライブラリ（TanStack Query・SWR）は**使わない**。データのほとんどは WebSocket で届き、HTTP はルーム作成・参加・「自分は誰か」程度なので、`fetch` ＋ Zod で検証する薄い関数で済ませる。
  - 状態管理は **Zustand**。状態の更新ロジックは「今の状態＋サーバーからのメッセージ → 次の状態」を返す純粋な関数（リデューサー）として React に依存せず書き、Zustand はその入れ物と部分的な購読（セレクター）にだけ使う。WebSocket の受信処理は部品の外に置く。
    - 理由: 共通パッケージのメッセージ型とリデューサーをそのまま使え、追加の記述が最小。通信と表示を分けられる。開発ツールは Redux DevTools をつなげて使える。
    - 注意: セレクターで毎回新しい配列・オブジェクトを返すと再描画が止まらなくなるので、その場合は `useShallow` を使う。
    - 検討して採らなかった案: React 標準の Context ＋ useReducer（受信処理が部品の中に入る、関係ない部品まで再描画される）、Redux Toolkit（サーバーのメッセージ型と Redux のアクションが二重になる。共通のリデューサーを直接渡すと Redux 内部のアクションが届いて型と実際の動きがずれる）、Jotai（メッセージをアトムごとの更新に振り分ける必要があり、1つのメッセージで何が変わるかを見渡しにくい）。
  - フォーム（TanStack Form など）・表（TanStack Table）・状態遷移（XState）のライブラリは使わない。長いリストの仮想化（TanStack Virtual）は遅ければ後で入れる。
- バックエンドの HTTP の受け口（ルーム作成・参加・「自分は誰か」・WebSocket の接続開始）は **Hono** で書く。
  - 理由: 型付きクライアント（サーバーの定義からフロントの呼び出し関数の型が作られる）、Cookie などの部品が標準でそろう、Workers で最もよく使われている。画面ファイルの配信は Workers の静的アセット配信に任せる。
  - 検討して採らなかった案: 素の `fetch` 関数（URL の判定・Cookie・型付けを自前で書く）、itty-router（振り分けのみで、フロントとの型の共有は自前）。
- ルームの Durable Object での WebSocket の扱い（接続の受け入れ・受信・送信・切断・休止からの復帰）は、**Durable Objects の標準 API を直接使い**、型付けと検証だけを薄い自作の層で包む。
  - 自作の層の案: 接続に付ける情報（`serializeAttachment`）の型と Zod での検証、共通パッケージのメッセージ型しか送れない `send`、受信メッセージの Zod での検証。
  - 理由: PartyServer の「接続情報に型が付く」利点は型引数による宣言だけで、境界を実行時に検証する方針では結局自分で検証を挟むため、ほぼ意味がない。ライブラリの仕様変更に追従する手間を避けたい。その他の便利さ（`broadcast` など）は標準 API でも数行で書け、送り分けが細かいこのアプリでは効きにくい。
  - 検討して採らなかった案: PartyServer（上記。加えて URL の形の前提が Cookie の `Path=/r/<ルームID>` と合わず、接続前の本人確認の仕組みも Hono 側で行うので使わない）、Agents SDK（AI エージェント向けで、状態を全員に同期する作りが細かい送り分けに向かない）。
  - クライアント側の自動再接続ライブラリ（partysocket など）は、サーバー側と独立に使える。採否はフロントの実装時に相談する。
- Worker から ルームの Durable Object への受け渡しは、**基本は Durable Objects の RPC**（ルームのクラスのメソッドを Worker から型付きで直接呼ぶ。公式も新規プロジェクトに推奨）とし、**WebSocket の接続開始だけ `fetch`**（HTTP の要求をそのままルームに渡す必要があるため）を使う。
  - RPC は Workers の実行環境に組み込まれた機能で、追加のライブラリや定義ファイルは不要。Worker とルームは一緒にデプロイされるので、両者の型の食い違いは起きにくい。
- HTTP の API の型の共有: フロントからは **Hono の型付きクライアント**で呼ぶ（URL・パラメータ・送る中身が型でチェックされる）。送る中身・返す中身の**スキーマは共通パッケージに置き**、サーバーは受け取った中身を（Hono の検証部品で）、フロントは返ってきた中身を、**それぞれ実行時に検証する**。WebSocket のメッセージも同じ共通パッケージのスキーマを使う。
  - 返ってきた中身も検証する理由: 型付きクライアントは型を付けるだけで検証しない。デプロイの瞬間に古い画面を開いていた人は、古いフロントのまま新しいサーバーと通信するため、食い違いうる。食い違ったら「更新してください」と出せる。
- スキーマ検証のライブラリは **Zod（v4）** とし、フロント・バック・保存で共通に使う。区別できる型（`RoomId` など）は `.brand()` で作る。
  - 理由: 情報量が最も多く、Hono や Cloudflare の例も Zod が中心。弱点のサイズ（フロントで十数 KB 大きい）と速さは、このアプリでは効かない（タップは多くても毎秒200件程度）。サイズが気になれば軽量版の Zod Mini に切り替えられる。
  - 検討して採らなかった案: Valibot（非常に小さいが、サイズの差がこのアプリでは効かない）、ArkType（最も速いが、独特の書き方とエディタの重さ、情報量の少なさ）。
- パッケージ管理は **pnpm 12 系**（2026-11 時点の最新。`package.json` の `packageManager` で固定）。モノレポはワークスペース機能だけで管理し、Turborepo・Nx などは入れない（パッケージが3つ程度なので不要。遅くなったら後で足す）。
  - 理由: 宣言していないパッケージを `import` できない厳しさ（ゲームロジックの独立も道具が守る）、インストール時のスクリプト実行を既定で止めるなどの安全対策、ワークスペース機能の充実。
  - 検討して採らなかった案: npm（宣言していないパッケージを使えてしまう）、Bun（実行環境としては使わないので利点は速さだけ）、Yarn v4（独特の仕組みでツールとの相性問題が出やすい）。
- リンターは **ESLint ＋ typescript-eslint（厳格な設定 strict-type-checked）**、フォーマッターは **Prettier**。
  - 背景（2026-11 時点）: TypeScript 7.0（Go 製）が 2026-07 に正式リリースされたが、外部ツール用の API がなく（7.1 で新 API の予定）、typescript-eslint は TypeScript 7 の上では動かない。公式案内の通り TypeScript 6 を並べて入れる（詳細は tsconfig の論点で決める）。
  - 理由: リンターに求めるのは速さより厳格さと確実さ。typescript-eslint の厳格な設定がそのまま使え、React 公式のフックのルールも使える。遅さはこの規模では問題にならない。
  - 検討して採らなかった案: Oxlint（型を使ったリントが 2026-07 に安定版。TypeScript 7 だけで済み非常に速いが、typescript-eslint の61ルール中59ルールの対応で、安定版になって日が浅い。実績がたまったら移行を検討する。移行用の道具もある）、Biome（独自の型推論で、ルールも判定の正確さも typescript-eslint とは別物）。フォーマッターの Oxfmt はベータ版のため見送り。
- テストは **Vitest 5**（2026-09 リリース。当初 4 としていたが、新規なので最新の系列にした）を全層で使う。サーバー（Worker・Durable Object・保存領域）は Cloudflare 公式の **@cloudflare/vitest-plugin**（2026-08 に @cloudflare/vitest-pool-workers から改名。Vitest 4.1 以降・5 に対応）で本番と同じ実行環境を手元で動かしてテストする。ゲームロジックは **fast-check** によるプロパティベーステストも使う。
  - 力の入れ方: ゲームロジックを最も手厚く（例のテスト＋性質のテスト。例: 確率は 0〜1、マスを開けても期待抽選回数は増えない、包除原理の結果がシミュレーションと一致、盤面の回転・反転で不変）。サーバーは認証・検証・順番が大事な処理・休止からの復帰を中心に。フロントはリデューサーを中心にし、画面の部品のテストは控えめ。
  - 画面の部品のテストの道具（Testing Library など）、E2E（Playwright が有力）、負荷試験（k6 か自作）の道具は必要になったときに決める。
  - 作りの方針: **乱数と現在時刻は外から渡せるようにする**（抽選・カード生成・順位決定ゲームの番号割り当て、Cookie の期限など）。テストで結果を固定できるようにするため。
- **React Compiler** を使う（コンパイル時に自動で不要な再描画を防ぐ。書き方は変わらない）。安定版の Babel 版（`babel-plugin-react-compiler`）を `@rolldown/plugin-babel` 経由で使う（Vite 8 と @vitejs/plugin-react 6 の公式の方法。Babel は React Compiler が 7 系の型に依存しているため 7 系）。
  - 検討して採らなかった案: Rust 版（`oxc-transform-react`。2026-11 時点で実験的）。
  - React 公式の ESLint プラグイン **eslint-plugin-react-hooks**（推奨設定 `recommended-latest`）を入れ、React Compiler が前提にしている決まり（フックの呼び方、描画中に状態を変えないなど）を破った箇所をリントで見つける。
- 開発中は **Cloudflare の Vite プラグイン（@cloudflare/vite-plugin）** で、Vite の開発サーバーの中で Worker と Durable Object を動かす（2026-11-15 に確定）。コマンドは `pnpm dev` 1つ。
  - 理由: 開発中も画面と API・WebSocket が同じ URL になり、Cookie と Origin の確認が本番と同じ条件で動く（開発中だけの分岐がコードに入らない）。どの URL を Worker に回すかのルールが `wrangler.jsonc` の1か所で済む。本番用のビルドも `vite build` 1つで画面と Worker をまとめて作れる。
  - `apps/web` の Vite の設定から `apps/server/wrangler.jsonc` を指定して使う。ビルド結果は `apps/web/dist`（`client` が画面、`bingo` が Worker と設定）。
  - 骨組みで、開発サーバー経由の画面・API・Durable Object の RPC・WebSocket（Hibernation API、2接続が同じルームにつながる）が動くことを確認した。
  - 検討して採らなかった案: Vite と `wrangler dev` を別々に起動し、Vite の中継（プロキシ）で API と WebSocket を転送する（振り分けのルールを2か所で揃え続ける必要があり、Origin の確認に開発用の分岐が入るおそれがある）。
- 画面の URL の振り分けは **TanStack Router のファイルベースのルーティング**（`src/routes` のファイル構成が URL になる）で、画面ごとのコード分割（`autoCodeSplitting`）を使う。生成される画面の一覧 `routeTree.gen.ts` は TanStack 公式の推奨に従いリポジトリに含める（CI で型チェックするのに必要）。
- **Screen Wake Lock API** で、ゲーム中のプレイヤー画面を消さない（iOS Safari 16.4 以降で対応）。
- 参加用の QR コードは旧実装と同じ **qrcode.react** で生成する。
- 検討して採らなかった技術:
  - GraphQL: データの大部分はサーバーから WebSocket で押し出すもので、HTTP の API は数個、クライアントも自分のフロントだけなので、スキーマ・サーバー・クライアントの仕組みが加わる重さに見合わない。
  - tRPC（Hono の型付きクライアントと役割が重なる）、gRPC / Protocol Buffers・MessagePack（メッセージが小さく効果がない）、SSE（一方向で、双方向が必要）、WebTransport（iPhone の対応が不十分）。
  - PWA（Service Worker）: 不要。
- スタイルは **SCSS ＋ CSS Modules**（`*.module.scss`）。SCSS のコンパイラは **`sass`**（当初 `sass-embedded` としていたが、骨組みで変更）。
  - 変更の理由: クラス名の型を作る happy-css-modules が内部で `sass` を直接読み込むため。Vite も `sass` を使えるので、1つに揃えると依存が減り、型の生成と実際の出力が同じコンパイラになる。`sass-embedded` の利点（速さ）は、この規模では差が出ない。
  - 色・余白などのデザインの値は **CSS 変数**で持つ（実行中に変えられるように。将来ルームごとの色やキャラクターの差し替えなどに備える）。Sass の変数とミックスインは画面幅の区切りなど固定の値に、繰り返しは演出の `@keyframes` の生成などに使う。
  - 読み込みは `@use`（`@import` は非推奨・廃止予定）。
  - CSS Modules のクラス名の型を自動生成し、打ち間違いをコンパイルエラーにする。道具は **happy-css-modules**（2026-11-15 に確定）。
    - 使い方: `pnpm dev` で Vite と同時に監視モード（`hcm --watch`）を動かし、SCSS を保存するたびに型ファイル（`*.module.scss.d.ts`）を作り直す。型チェック（CI を含む）の前にも1回実行する。型ファイルはリポジトリに含めない。
    - 理由: Vite から独立した道具なので、Vite のバージョンアップの影響を受けにくい。CI の手順が単純（型チェックの前に1回実行するだけ）。型ファイルから SCSS の該当行に飛べる。
    - Vite の型（`vite/client`）は `*.module.scss` を「どんな名前でも通る」型で宣言しているため読み込まず、`import.meta` の型だけを使う。こうすると、型ファイルが無いときもコンパイルエラーになる。
    - 検討して採らなかった案: vite-css-modules（Vite の内部の処理を置き換える作りで、バージョンアップのたびに壊れないか気にする必要がある。CI で型チェックの前にビルドするか、型ファイルをリポジトリに含める必要がある）、typescript-plugin-css-modules（エディタの中でだけ型が付き、`tsc` や CI では検出されない）。
  - 検討して採らなかった案: Tailwind CSS v4（旧実装で使用。書く速さと情報量は最大だが、クラス名がただの文字列で型の原則に沿いにくい）、Panda CSS（型は強いが情報量が少なく、依存とビルド時のコード生成が増える）、素の CSS Modules（SCSS のミックスインと繰り返しを使いたい）。
- UI 部品のライブラリは**使わない**。ダイアログはブラウザ標準の `<dialog>` 要素、メニューなどは popover 属性で作る。iPhone での背面スクロールの停止などの不足分は少量のコードで補う。足りなければ、その部品だけ Radix などを入れる。
  - 理由: 必要な部品がダイアログとメニュー程度と少なく、標準機能でほぼ足りる。恩恵が小さいところで依存を増やさない。
  - 検討して採らなかった案: 見た目込みの部品集（MUI など。独自の見た目が中心なので不要）、ヘッドレスの部品（Radix・React Aria・Base UI）、shadcn/ui（旧実装で使用）。
- 悪意のある大量の要求への対策のうち、軽いものは**最初から入れる**: ① ルームの参加人数の上限（ルームの設定として持つ）、② 接続ごとの送信回数の制限（短時間に送れるメッセージ数を超えたら無視または切断する。人間のタップは多くても毎秒数回）。
- Node.js と pnpm の版は **mise** で管理する。リポジトリの `mise.toml` に Node.js 26 系・pnpm 12 系を書き、このフォルダに入ると mise が自動でその版を使う（他のプロジェクトには影響しない）。CI でも mise の公式の部品（`jdx/mise-action`）を使う。
  - 理由: corepack は Node.js 25 から同梱されなくなり（手元の古い corepack では pnpm 12 を起動できなかった）、Volta は 2025-11 に保守終了。mise は手元に既に入っていた。
  - 検討して採らなかった案: corepack を更新する、pnpm 12 をグローバルに入れる（どちらも nvm の Node.js 全体に影響する）。
- Node.js は **26 系（2026-11 時点の Active LTS）** に固定する。`package.json` の `devEngines.runtime`（`onFail: "download"`）で指定し、pnpm に自動でダウンロードさせる（手元に入っている Node.js の版に関係なく、このプロジェクトでは 26 系が使われる。正確な版はロックファイルに記録される）。次の LTS（28 系）が出たら番号を書き換える。
- 依存パッケージの安全対策:
  - **公開から3日（`minimumReleaseAge: 4320`）たっていないバージョンは入れない**（pnpm 12 の既定は1日）。乗っ取られた悪意あるバージョンは数時間〜数日で見つかって取り下げられることが多いため。緊急のセキュリティ修正は `minimumReleaseAgeExclude` に一時的に書いて入れる。
  - 依存パッケージのビルドスクリプトは、`allowBuilds` で許可したもの以外は実行しない（pnpm 12 の既定）。現在許可しているのは esbuild（ビルド道具）と workerd（Cloudflare Workers の実行環境）だけ。`@parcel/watcher`（sass が使うファイル監視）は、配布済みのバイナリが無い環境向けの予備のビルドなので明示的に止めている。
  - CI ではロックファイルに書かれたバージョン以外を入れない（`--frozen-lockfile`）。
  - GitHub Actions の外部の部品は、タグではなくコミットの SHA で固定する（タグの書き換えによる乗っ取り対策）。部品の更新にも「公開から3日」の考え方を当てはめる。
- **CI（GitHub Actions）** で、push のたびに型チェック・リント・テストを実行する。
  - main は GitHub の Ruleset（「main を守る」）で保護する（2026-11-15 に設定）: 直接の push を禁止して PR からだけ取り込む、CI（`check`）が合格しないとマージできない、強制 push と削除を禁止。承認の人数は 0（一人で開発しているため）。例外を許す人は置かない（管理者も同じ）。
  - CI と Copilot のコードレビューは別物。Copilot のレビューは AI のコメントで、利用枠を使う。動かなくても CI の守りは変わらない。
- サーバーの Cloudflare の API の型は `wrangler types` で生成した `apps/server/worker-configuration.d.ts` を使い、リポジトリに含める（型チェックの前に `wrangler types --check` で最新かを確かめる）。
- 内部のパッケージ（game・protocol）はビルドせず、`package.json` の `exports` で TypeScript のソースを直接指す（Vite・Wrangler・Vitest がそのまま読める）。
- パッケージの名前は `@bingo/` を頭に付ける: `apps/web`（`@bingo/web`）、`apps/server`（`@bingo/server`）、`packages/game`（`@bingo/game`。ゲームロジック）、`packages/protocol`（`@bingo/protocol`。WebSocket のメッセージと HTTP の API のスキーマ）。
- フロントエンド・バックエンド・共通ロジックを分けたモノレポ構成にする（`apps/web`、`apps/server`、`packages/game`、`packages/protocol`）。

### 保存方法
- Durable Objects の保存には**キーと値の API**（`storage.get` / `storage.put`）を使い、SQL は書かない。
  - 理由: SQLite の型の甘さを避けたい。この API は値を JavaScript の値のまま保存するため、SQLite の列の型の影響を受けない。
- 保存・読み込みはスキーマ検証（Zod）を行う薄い層で包む。

### 型安全の方針
- **型に関してできることはできる限りやる**ことを開発の原則とする。
- 具体策（2026-11-12 に確定）:
  - **TypeScript 6** を使う（型チェックもリンターも）。TypeScript 7 は typescript-eslint が対応したら（7.1 以降の見込み）まとめて上げる。7 と 6 を並べる方法は、どちらで動いているかを気にする場面が増えるので採らない。規模的に 6 でも型チェックは数秒。
  - tsconfig: `strict`（6 から既定）に加えて、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitReturns`、`noFallthroughCasesInSwitch`、`noImplicitOverride`、`noPropertyAccessFromIndexSignature`、`allowUnreachableCode: false`、`allowUnusedLabels: false`、`erasableSyntaxOnly`（`enum`・`namespace` を禁止し、文字列のユニオン型を使う）、`verbatimModuleSyntax` を有効にする。使っていない変数の検出は ESLint に任せる。
  - 共通の tsconfig を1つ作り、各パッケージはそれを読み込んで、使える実行環境の API だけを変える: ゲームロジックと共通パッケージは **JavaScript の標準機能のみ**（DOM も Cloudflare の API も型として存在しない）、`apps/server` は Workers の API（`wrangler types` で生成）、`apps/web` は DOM。ゲームロジックの独立を、pnpm（宣言していないパッケージを使えない）と合わせて道具で守る。
  - 外部との境界（WebSocket メッセージ、HTTP の要求と応答、保存領域、接続に付ける情報）はすべて実行時に Zod で検証する
  - フロントエンドとバックエンドのメッセージ型は共通パッケージで定義し、判別可能なユニオン型で表す
  - ID や番号などは区別できる型にする（例: `RoomId` と `PlayerId` を取り違えられない、番号は 1〜75 に限定）。Zod の `.brand()` で作る
  - `any` を禁止し、switch の網羅性を型でチェックする（ESLint ＋ typescript-eslint の strict-type-checked を使う）

### 想定規模・料金
- 利用場面: 会社のイベント、大学祭など。
- 同時開催のルーム数: 多くても3つ程度の見込み。ただし、必要なときに必要な分だけ自動で規模が拡大できること。
  - Durable Objects はルームごとに独立した実体が自動で作られるため、ルーム数の増加には設定なしで対応できる。
  - 1ルーム内の上限は1つの Durable Object の処理能力で決まる。設計目標は **1ルーム1000人**とし、負荷試験で確認する。数千人規模（1ルームを複数の実体に分ける設計が必要）は対象外。
- 料金プラン: Cloudflare Workers の有料プランを契約済み（ポートフォリオサイトの運用と同じアカウント。含まれる利用枠は共有になる）。

### 画面構成
- ホスト画面は操作用と投影用に**分けない**（旧実装と同じく1画面）。
- 上位3人・下位3人のカード表示（ホストのゲーム画面）と、最下位の人のカード表示（結果画面）は**引き継ぐ**。カードはプレイヤーが開けた状態で表示する。
- プレイヤーのゲーム画面:
  - 確率・順位などの自分の情報、カード、キャラクターと吹き出しを表示する。
  - カードの上にプレイヤー名を表示する。
  - 最新の抽選番号は吹き出しで伝える。抽選された瞬間の演出も行う。
  - 順位決定ゲームの表示を行う（自分の番号・抽選番号・結果、参加しない人には進行中であること）。
  - 接続状態を表示する（通信が切れて再接続中であることが分かるように）。
  - メニュー（右上など）から、ルールの確認、抽選履歴の確認（メニュー → 抽選履歴を確認 → 履歴ダイアログ）ができる。ルーム名もメニュー内に表示する。
  - 景品獲得後もゲームを続けられる。景品獲得に関する確率（A・G・H）は「—」表示に変える。
- ホスト画面には抽選履歴を常時表示する。
- ゲーム終了後は、プレイヤーにも全体の最終ランキングを見せる。

### 順位の扱い
- 景品を獲得した人は順位を確定する。
- 順位が確定していない人の中で順位を争う。表示上の順位も確定していない人の中で付け直す（例: 1位が確定したら、それまで2位だった人が1位になる）。
- ゲーム終了時、景品を獲得していない人の最終順位は、その時点のゲーム中のランキング（期待抽選回数の順）をそのまま確定させる。景品獲得者の後ろに並ぶ。

### 景品獲得ライン（winLine）
- 残す（実運用で「2本ビンゴで景品獲得」のルールを使うことがある）。
- 順位決定ゲームの「同時ビンゴ」、ランキングの期待抽選回数は、いずれも**景品獲得ラインに達すること**を基準にする。

### 同時ビンゴの順位決定ゲーム
- 「同時」の定義: **同じ抽選回の間（次の番号が抽選されるまで）にビンゴした人**を同時ビンゴとして扱う。押し忘れて次の抽選後に押した人は、その押した回のビンゴとなる。
- 手順:
  1. 同時ビンゴした人に、1〜75 の番号を**重複なし**でランダムに振る。
  2. ホストが抽選する。この箱は本抽選（75個の箱）とは**独立した別の箱**（1〜75）。
  3. 抽選番号との距離が近い順に順位を付ける。
  4. 同じ距離の人がいれば、その人たちだけで同じゲームをやり直す。
- 同時ビンゴが76人以上の場合は、番号の**重複を許す**（全員に重複なしで振れないため）。同じ番号の人は距離が必ず同じになるので、手順4の再戦で処理される。
- 順位決定ゲームの間、本抽選は**一時停止**する。

### ゲーム終了
- 次のいずれかで終了する:
  - ホストが「ゲーム終了」を押す
  - 全員の順位が確定する
- 景品の数が設定されている場合、最後の景品が確定した時点で「ゲームを終了しますか？」というダイアログをホストに表示する。

### プレイヤーの再接続
- 画面を閉じた・再読み込みしたときは、**参加時にサーバーが発行するトークンを HttpOnly Cookie に入れる**方式で同じプレイヤーとして戻る。ログインは不要。
  - 参加: 名前を HTTP（例: `POST /r/<ルームID>/join`）で送ると、サーバーが推測できない乱数（128ビット以上）のトークンを作り、`Set-Cookie` で返す。
  - Cookie の属性: `HttpOnly`（JavaScript から読めない）、`Secure`、`SameSite=Strict`、`Path=/r/<ルームID>`（ルームごとに別のトークン）、`Max-Age`（24時間程度。値は実装時に確定）。
  - 接続: WebSocket の接続開始時にブラウザが Cookie を自動で付ける。Worker が **Origin ヘッダー**を確認し、Cookie からトークンを取り出してルームの Durable Object に渡す。トークンのハッシュ値はルームの保存領域にあるので、**照合はルームの中で行う**。接続を受け入れる時点で本人が確定する。
  - サーバーはトークンそのものではなく**ハッシュ値**を保存する。
  - 同じトークンで2つ目の接続が来たら**新しい接続を優先**し、古い接続は「別の画面で開かれました」と表示して切る（再読み込み直後に古い接続が残っていても戻れるように）。
  - 参加用 URL を開いたとき、JavaScript は Cookie を読めないので、サーバーに「自分は誰か」を問い合わせる。有効なトークンがあれば名前入力を飛ばして待機画面またはゲーム画面に戻す。
- これに伴い、**画面と API・WebSocket は同じサイト（同じ登録ドメイン）で配信する**（Workers の静的アセット配信で1つの Worker から出す想定）。
- XSS 自体の対策（フレームワークの自動エスケープ、CSP）は別に行う。HttpOnly で防げるのは「トークンを盗んで後から使う」ことだけで、ページを開いている間の操作は防げないため。
- 既知の制限: QR コードから LINE などのアプリ内ブラウザで開いた場合、Safari / Chrome とは Cookie が共有されないため、別のブラウザで開き直すと戻れない（「端末を変えた場合」の論点で扱う）。
- 検討して採らなかった案:
  - localStorage / sessionStorage / IndexedDB にトークンを保存: XSS で読み取られる（IndexedDB でも同じ）。sessionStorage はタブを閉じると消える。
  - 取り出せない鍵（WebCrypto の `extractable: false` の鍵で、サーバーのチャレンジに署名する）: 安全性は Cookie 方式とほぼ同等で、CSWSH や盗聴の心配が構造的にない利点はあるが、自前の認証手順の実装・検証の負担が増える。画面と API を別サイトで配信する必要が出たら再検討する。
  - URL にトークンを入れる: 履歴・スクリーンショット・画面共有から漏れやすい。
  - パスキー: 数百人が QR から参加する場面には重すぎる。
  - DBSC: iPhone の Safari で使えない。
  - Cookie ＋ 使い捨てチケット: 画面と API を別ドメインにする場合の方式で、今回は不要。

### 端末・ブラウザを変えた場合
- **対応しない**。Cookie が見つからない端末・ブラウザからは、新しいプレイヤーとして参加し直す（カードも新しくなる）。
  - 想定した場面: (a) QR を LINE などで読んでアプリ内ブラウザで参加し、後で Safari / Chrome から開き直す、(b) 電池切れで別のスマホから入り直す、(c) プライベートブラウズのタブを閉じた・Cookie を消した。b・c は起こりにくいので救わない。
- 最も起こりやすい (a) は、起こりにくくする:
  - 参加用 QR の URL に、LINE で外部ブラウザを開かせる指定（`openExternalBrowser=1`）を付ける。仕様は実装時に LINE の公式で確認する。
  - それ以外のアプリ内ブラウザで開かれたことを検出したら、参加画面に「Safari / Chrome で開くと、閉じても戻りやすくなります」と案内する。参加は止めない。
- 検討して採らなかった案: 名前＋合言葉での復帰（全員の参加の手間が増える、忘れる）、ホストの承認での引き継ぎ（困る人が少なく、仕組みを作るほどではない）、引き継ぎコードの表示（元の端末が使えない場面に効かない）。

### ホストの本人確認
- ルーム作成時（「募集開始」を押したとき）にホスト用のトークンを発行し、**HttpOnly Cookie** に入れる（属性・ハッシュ保存・Origin 確認はプレイヤーと同じ）。プレイヤー用とは別の Cookie 名にし、サーバーはホストとプレイヤーを区別して扱う。
- 同じトークンで2つ目の接続が来たら新しい接続を優先する（プレイヤーと同じ）。
- 端末・ブラウザを変えた場合には**対応しない**。戻れなければルームを作り直す。
- 検討して採らなかった案:
  - 復旧コード（作成時に1度だけ表示し、別の端末で入力して戻る）: 止まって困る規模・用途は将来のアカウントで対応する。
  - 秘密の管理用 URL: ホスト画面はプロジェクターに投影されるため、アドレスバーから会場に漏れる。

### アカウント・収益化（将来）
- 将来はきちんと作って収益化したい。そのときはホスト用のアカウントが必要になる（小規模ならアカウントなしで使え、ホストが止まったときの対処はない。止まって困る用途はアカウントで対応する、という位置づけ）。
- **今は作ることを優先し、収益化の話はモノができあがってから行う**。アカウントも今は作らない。プレイヤーはアカウント不要のまま。
- 方針: ログイン（本人確認）と決済・プラン管理は**ビンゴとは別のサイト・サービスに置く**。ビンゴのサイトは、受け取った本人情報と権利（人数上限など）の確認だけを持つ。ログインは認証サイトに移動して戻ってくる一般的な流れ（OpenID Connect など）を想定。具体的な方式は収益化の話のときに決める。
- 今の設計で守ること:
  1. 「このルームのホストか」の判定を1か所にまとめ、後でアカウントによる判定を足せるようにする。
  2. 人数上限や使える機能はコードに直接書かず、ルーム作成時に決まるルームの設定として持つ。今は全ルーム同じ値を入れる。

### 景品獲得ライン未満のビンゴ・リーチの意味
- **リーチ**は、ホスト画面・プレイヤーとも**ライン基準**（どれかのラインがあと1マスで完成する状態）とする。景品獲得ラインが2本以上でも同じ。
  - 検討して採らなかった案: ホスト画面だけ景品基準（あと1マスで景品獲得ラインに達する人だけをリーチとする）にする。
- 景品獲得ライン未満のビンゴ（例: 2本ルールでの1本目）:
  - プレイヤーのキャラクターが「ビンゴ！あと1本で景品」のように、ビンゴしたことと景品までの残りを言う。
  - プレイヤーの情報表示は E（ビンゴ 1 / 2）が進むだけで、追加はない。
  - ホスト画面の名前表示にも出す（「○○さん ビンゴ 1/2」）。景品獲得より控えめにし、見分けがつくようにする。
  - 景品獲得ラインが1本のときは、ビンゴ＝景品獲得なのでこの区別は出てこない。
- 1マスで2本以上のラインが同時に完成した場合は、そろった本数をそのまま数える（2本ルールなら一気に景品獲得）。キャラクターは「ダブルビンゴ！」のように言う。

### 演出と音
- 背景: 利用者から「もっと派手な演出」の要望をもらっている。
- 道具は **CSS（SCSS の `@keyframes`）＋ Motion ＋ canvas-confetti** を基本にする。
  - CSS: マスを開けるなど単体の軽い動き。
  - Motion: 抽選演出の流れの組み立て、吹き出しの出入り（消えるときの動き）、ランキングや順位決定ゲームの並び替え、ばねの動き。
  - canvas-confetti: 紙吹雪・花火などのパーティクル。
  - ホスト画面で必要になれば、後で WebGL（PixiJS など）を足す。プレイヤーのスマホは性能差があるので控えめにする。
  - キャラクターの動かし方（1枚の絵／表情の差し替え／Lottie／Rive）はキャラクターのデザインの論点で決める。当面は仮の図形を Motion で動かす。キャラクターは「状態（普段・喋る・喜ぶ・知らせる など）」を受け取るだけの部品にし、後で差し替えられるようにする。
- 演出の考え方: 溜め・じらし・一気に解放（光・揺れ・音・粒を同時に）・珍しい出来事ほど大きく（リーチ < ビンゴ < 景品獲得 < ダブルビンゴ）。
  - プレイヤーのスマホでは、抽選の瞬間に「カードにある」ことを示す演出はしない（探す楽しさを残す方針）。スマホの大きな演出は、自分でマスを押してリーチ・ビンゴ・景品獲得がそろった瞬間に集中させる。
- **スマホへの抽選番号の公開は、ホスト画面の発表の瞬間に合わせる**（ホスト画面で溜めている間にスマホに番号が出るネタバレを防ぐ。作り方は実装時に決める）。
- **音はホスト画面・プレイヤー画面の両方で鳴らす**。
  - ホスト画面: 抽選（ドラムロール・発表）、リーチ・ビンゴ・景品獲得、順位決定ゲームなど。「ゲーム開始」を押したときに音を有効にする。
  - プレイヤー画面: 自分の操作に対する音（マスを開ける、リーチ、ビンゴ、景品獲得、抽選されていない番号を押した）。**抽選の瞬間には鳴らさない**（数百台が同時に鳴って騒がしく、ホスト画面の音を邪魔するため）。参加ボタンを押したとき（再読み込みで戻った人は最初にマスを押したとき）に音を有効にする。
  - iPhone ではマナーモードに従わせる（Audio Session API。実装時に挙動を確認）。
  - 両画面に**スピーカーマークのオン／オフボタン**を置く。最初はオン。設定は端末に保存する（localStorage）。
  - 音は Web Audio API で、あらかじめ読み込んだものを鳴らす（押した瞬間に鳴らすため）。プレイヤーは参加後に読み込む。
- 進め方: 骨組みができたら早めにホスト画面の抽選演出を試作し、見ながらタイミングや派手さを調整する。効果音は、まず利用条件を確認した無料の素材で試す。
- **ホスト画面の抽選演出はガラガラ（回転抽選器）**にする（2026-11-15 に確定）: ガラガラが回る（溜め）→ 玉が出口から飛び出し、坂を転がって受け皿に入る → 玉が寄って大きくなり、番号を発表する（光の筋・白い光・揺れ・紙吹雪を同時に）。
  - ガラガラの中は描かない（本物と同じく外見だけ。かき混ぜは回転と音で表す）。そのため物理エンジンは使わず、**SVG ＋ Motion で動きの長さを決めて描く**。長さが毎回正確に決まるので、音や、スマホへの番号の公開の瞬間と合わせやすい。
  - どの番号を出すかは外（本番ではサーバー）が決め、演出の部品（`DrawStage`）は見せ方だけを受け持つ。番号が見えた瞬間に呼ばれる関数を受け取り、スマホへの公開をそこに合わせる。
  - 本物の抽選器に合わせる: 出口は胴の縁の**銀色の口金**で、胴と一緒に回る。**回っている途中**で口金が受け皿側を向いた瞬間に玉が飛び出し、胴はその後も惰性で少し回って止まる。回し方は「最初に加速し、その後は一定の速さ」（手で回す感じ）。
  - 見た目: 胴・台は**木の質感**（木目・縁の陰影・角の金具。光の反射は胴が回っても動かない）。坂は銀色の金属の樋で、受け皿の箱の左の板の上を越えて箱の中に少し張り出す（板にめり込まない高さを通す。下の端の柱は箱より手前に立てる）。**受け皿は赤い毛せん張りの木の箱**（本物の木製の抽選器でよく使われる形。玉は小さく1回跳ね、少し転がって止まる。玉の下の方は箱の手前の板に隠れる）。口金の穴は描かない。
    - 検討して採らなかった案: 金属の皿（玉が何度も跳ねて派手だが、毛せんの方が木の胴と合う）。
  - 玉には**数字だけ**を書く（列の文字 B・I・N・G・O は分かりにくいので書かない）。色は列ごとに分ける（B 青・I 赤・N 白・G 緑・O 黄）。寄ってくる間は色だけが見え、発表の瞬間に番号が見える。
  - 音を鳴らすきっかけを演出の部品から知らせる: 回し始め（回転の予定つき）・玉が飛び出す・玉が落ちる（金属の坂か毛せんの受け皿か、強さつき）・坂を転がる・発表。
  - **効果音は「効果音ラボ」（https://soundeffect-lab.info/）の録音素材を使う**（2026-11-15 に決定）。
    - 規約（2026-11-15 に確認）: 商用利用は無料、クレジット表記は任意、アプリへの組み込みは可（「音源ファイルむき出しでも可」）。素材の再配布は禁止。ソースコードの公開についての記載はない。
    - リポジトリは公開しているので、音のファイルは **`apps/web/public/sounds/` に置き、`.gitignore` で除外する**。取得元の一覧（ページと音の名前とファイル名）は `apps/web/src/sound/sources.ts` に記録し、ファイルを失っても取り直せるようにする。ファイルが無い環境（CI など）では、その音が鳴らないだけで動く。効果音ラボはプログラムからのダウンロードを受け付けない（403）ので、ブラウザから手で取得する。
    - 将来デプロイを自動にするときは、デプロイする環境に音を届ける方法（Cloudflare R2 など）を決める。
    - 使い方: ガラガラは「抽選機を回すガラガラ」を回す長さに合わせて繰り返し、回る速さに合わせて音量と高さを変える。素材のままでは軽い玉の「カラカラ」に聞こえたので、再生を遅くして低くし、高い音を削って低い音を足し、高さとずらした位置を変えたもう1つを重ねて重くしている。「抽選機から玉が出る」は受け皿に落ちたときに丸ごと、飛び出す瞬間と坂に当たる瞬間には最初の「コトッ」だけを鳴らす（坂は少し高くする）。坂を転がる音は合う素材がないので鳴らさない。
    - 発表の音（ジャジャーン／ジャン！／ロールの閉めシンバル／ラッパのファンファーレ）、ドラムロール（なし／じらしの間／回し始めから）、歓声と拍手（重ねるか）は、試作画面で切り替えて比べている（どれにするかは未決定）。ジャジャーンは迫力が強すぎたので音量を半分ほどに抑えた。ラッパは盛り上がりの頂点が頭から 0.8 秒にあるので、発表の瞬間に頂点が来るよう早めに鳴らし始める。
    - 検討して採らなかった案: Web Audio API で合成する（一度作ったが、作り物っぽくユーザーの好みに合わなかった）、本物の抽選器を自分で録音する、Freesound の CC0 の音（ガラポンの録音が見つからなかった）。
  - 各段階の長さの初期値（ユーザーが試作画面で調整）: 玉が出るまで回す長さ 2 秒・回数 2 回、転がる 0.8 秒、じらし 0.6 秒、寄る 0.6 秒、見せる 4 秒。
  - 試作は、開発中だけ開ける画面（`apps/web/dev/draw.html`、URL は `/dev/draw`）で行う。サーバーにはつながず画面の中で番号を引き、各段階の長さをつまみで変えられる。本番のビルドは `index.html` だけが対象なので含まれない。
  - 検討して採らなかった案: 回る数字（スロット風）、玉が飛び回る演出、物理エンジン（Matter.js）で中の玉を動かす、3D（three.js）。
