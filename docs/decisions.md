# Bingo!2 作り直し — 決定事項ログ

旧リポジトリ: `hig270/syshack-bingo`（Next.js + Firestore）。本リポジトリで完全に作り直す。

## 目的（必須要件）

- 抽選結果のリアルタイム共有
- 確率のリアルタイム表示
- ビンゴカードのリアルタイム共有（ホスト画面での表示用）
- 数百人規模の参加に耐える

## 決定事項

### マスの開け方・押し忘れ
- マスはプレイヤーの手動操作でのみ開く。**自動オープン・自動強調表示はしない**。
  - 背景: 旧実装では当選番号を即座に強調表示し、離席時は自動で開けていたが、ユーザーから「紙のビンゴにあった探す楽しさが失われる」「自動で開くのは違和感がある」との意見があった。
- 抽選済みでない番号のタップはサーバーが受け付けない。

### 押し忘れ対策（キャラクターの吹き出し）
- 画面左上にキャラクターを置く。
- 普段はタップすると画面上部に吹き出しが出て何か喋る（数秒で消える）。
- 抽選番号がカードにあったのに開けないまま次の抽選が始まったら、キャラクターが「開け忘れがあるかも」などと吹き出しで知らせる。
  - 吹き出しは**開け忘れがある限り表示し続ける**（数秒で消えない）。開け忘れがなくなったら消える。
  - ヒントの詳しさは段階的に上げない（個数や場所は教えない）。
  - 開け忘れの吹き出しが出ている間は、キャラクターをタップしても何も起こらない。
- リーチ・ビンゴ・順位決定ゲームの開始などの演出も、まずはキャラクターの吹き出しで行う（派手な演出は後で検討）。
- キャラクターのデザインは未作成。当面は仮の図形で実装し、後でオリジナルのキャラクターに差し替える。
- 判定は端末内で完結する（抽選済み番号・自分のカード・開けたマスはすべて端末が持っている）。
- 出た番号の一覧（抽選履歴）はヒントではなく基本機能として扱う（ホスト画面に常時表示、プレイヤーはメニューから確認。詳細は「画面構成」）。

### ビンゴ判定
- ラインの最後のマスを押した瞬間に自動でビンゴ成立とする（申告ボタンは設けない）。
- 抽選番号上ではビンゴしていても、押していなければ押すまでビンゴとして扱わない。

### 確率表示・ランキング
- プレイヤーに見せる確率は、**プレイヤーが開けたマス**をもとに計算する。
- ホスト画面のランキングも**プレイヤーが開けた情報**をもとにし、タップ時に変動する。
- → タップは都度サーバーへ送信し、サーバー側で検証・集計する。

### ランキングの指標
- 旧実装のポイント制（開けたマス数＋ライン進捗点＋特定8マスボーナス）は**廃止**する。
  - 理由: 重み付けに根拠がない／ラインを 2/5→3/5 に進めても点が増えないバグ／ポイントの高さがビンゴへの近さと一致しない／5×5 固定で特殊モードに対応できない。
- 未達成者は**景品獲得ラインに達するまでの期待抽選回数**（あと平均何回の抽選で達するか）の小さい順に並べる。
  - 開けたマスを基準に計算する。見落としのマスは「まだ抽選されていない」ものとして扱う（実際の抽選状況を使うと見落としの存在が漏れるため）。
  - 角・斜めのマス、FREE を含むラインのマスの有利さは、確率計算から自然に反映される（検証済み）。
  - 計算はラインの組み合わせの包除原理で厳密に行う。タップのたびに、その人の分だけ再計算する。
  - 下位表示は期待抽選回数が最も大きい人たち。
- 期待抽選回数が同じ人は**同順位**とする。

### プレイヤー画面の確率・状況表示
- 当面は以下をすべて表示する（見せ方の取捨選択は後で検討）。
  - A. 景品獲得ラインに達するまでの期待抽選回数（ランキングと同じ値）
  - B. 次の抽選でビンゴ（ライン1本の完成）する確率
  - C. 5回以内にビンゴ（ライン1本の完成）する確率
  - D. 順位（例: #12 / 300人）
  - E. 景品獲得ラインの進み具合（例: ビンゴ 1 / 2）
  - F. 次の抽選番号が自分のカードのどこかに当たる確率
  - G. 次の抽選で景品獲得ラインに達する確率（景品獲得ラインが2本以上のときのみ）
  - H. 5回以内に景品獲得ラインに達する確率（景品獲得ラインが2本以上のときのみ）
- B・C の「ビンゴ」はライン1本の完成を指す。すでに1本以上ビンゴしている場合は、まだ完成していない**新しいライン**の完成を指す。
- 景品獲得ラインが1本のときは B=G、C=H なので G・H は表示しない。
- いずれも開けたマスを基準に計算する。分母（残りの番号数）は実際の残り番号数を使う。
  - 見落としが多いと、未開封マス数が残り番号数を超えて確率が 100% を超えうる（見落としがあるときだけ起きる）。その場合は 100% で頭打ちにする。

### 技術スタック・基盤
- 言語は**フロントエンド・バックエンドとも TypeScript**。
- 基盤は **Cloudflare Workers + Durable Objects**（1ルーム＝1つの Durable Object、WebSocket Hibernation を使用）。
  - 比較した候補: AWS（API Gateway / AppSync Events + Lambda + DynamoDB、ECS）、Go + Fly.io + PostgreSQL、Elixir/Phoenix、Django、配信専門サービス（Ably・Pusher・Supabase Realtime）。
  - 選定理由: ルームの状態を1か所で順番に処理できる、数百人への一斉配信の送信が無料、待機中の費用がほぼゼロ、運用の手間が少ない。
- ゲームロジック（カード生成・判定・確率計算・順位決定）は Cloudflare に依存しない独立したモジュールにする（将来の移行に備える）。
- フロントエンド・バックエンド・共通ロジックを分けたモノレポ構成にする（案: `apps/web`、`apps/server`、`packages/game`）。

### 保存方法
- Durable Objects の保存には**キーと値の API**（`storage.get` / `storage.put`）を使い、SQL は書かない。
  - 理由: SQLite の型の甘さを避けたい。この API は値を JavaScript の値のまま保存するため、SQLite の列の型の影響を受けない。
- 保存・読み込みはスキーマ検証（Zod など）を行う薄い層で包む。

### 型安全の方針
- **型に関してできることはできる限りやる**ことを開発の原則とする。
- 具体策（案。実装開始時に詳細を確定する）:
  - TypeScript の最も厳しい設定（`strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` など）
  - 外部との境界（WebSocket メッセージ、HTTP、保存領域）はすべて実行時にスキーマで検証する
  - フロントエンドとバックエンドのメッセージ型は共通パッケージで定義し、判別可能なユニオン型で表す
  - ID や番号などは区別できる型にする（例: `RoomId` と `PlayerId` を取り違えられない、番号は 1〜75 に限定）
  - `any` を禁止し、switch の網羅性を型でチェックする（typescript-eslint の厳格な設定を使う）

### 想定規模・料金
- 利用場面: 会社のイベント、大学祭など。
- 同時開催のルーム数: 多くても3つ程度の見込み。ただし、必要なときに必要な分だけ自動で規模が拡大できること。
  - Durable Objects はルームごとに独立した実体が自動で作られるため、ルーム数の増加には設定なしで対応できる。
  - 1ルーム内の上限は1つの Durable Object の処理能力で決まる。設計目標は **1ルーム1000人**とし、負荷試験で確認する。数千人規模（1ルームを複数の実体に分ける設計が必要）は対象外。
- 料金プラン: Cloudflare Workers の有料プランを契約済み（ポートフォリオサイトの運用と同じアカウント。含まれる利用枠は共有になる）。

### 画面構成
- ホスト画面は操作用と投影用に**分けない**（旧実装と同じく1画面）。
- 上位3人・下位3人のカード表示（ホストのゲーム画面）と、最下位の人のカード表示（結果画面）は**引き継ぐ**。カードはプレイヤーが開けた状態で表示する。
- プレイヤーのゲーム画面:
  - 確率・順位などの自分の情報、カード、キャラクターと吹き出しを表示する。
  - カードの上にプレイヤー名を表示する。
  - 最新の抽選番号は吹き出しで伝える。抽選された瞬間の演出も行う。
  - 順位決定ゲームの表示を行う（自分の番号・抽選番号・結果、参加しない人には進行中であること）。
  - 接続状態を表示する（通信が切れて再接続中であることが分かるように）。
  - メニュー（右上など）から、ルールの確認、抽選履歴の確認（メニュー → 抽選履歴を確認 → 履歴ダイアログ）ができる。ルーム名もメニュー内に表示する。
  - 景品獲得後もゲームを続けられる。景品獲得に関する確率（A・G・H）は「—」表示に変える。
- ホスト画面には抽選履歴を常時表示する。
- ゲーム終了後は、プレイヤーにも全体の最終ランキングを見せる。

### 順位の扱い
- 景品を獲得した人は順位を確定する。
- 順位が確定していない人の中で順位を争う。表示上の順位も確定していない人の中で付け直す（例: 1位が確定したら、それまで2位だった人が1位になる）。
- ゲーム終了時、景品を獲得していない人の最終順位は、その時点のゲーム中のランキング（期待抽選回数の順）をそのまま確定させる。景品獲得者の後ろに並ぶ。

### 景品獲得ライン（winLine）
- 残す（実運用で「2本ビンゴで景品獲得」のルールを使うことがある）。
- 順位決定ゲームの「同時ビンゴ」、ランキングの期待抽選回数は、いずれも**景品獲得ラインに達すること**を基準にする。

### 同時ビンゴの順位決定ゲーム
- 「同時」の定義: **同じ抽選回の間（次の番号が抽選されるまで）にビンゴした人**を同時ビンゴとして扱う。押し忘れて次の抽選後に押した人は、その押した回のビンゴとなる。
- 手順:
  1. 同時ビンゴした人に、1〜75 の番号を**重複なし**でランダムに振る。
  2. ホストが抽選する。この箱は本抽選（75個の箱）とは**独立した別の箱**（1〜75）。
  3. 抽選番号との距離が近い順に順位を付ける。
  4. 同じ距離の人がいれば、その人たちだけで同じゲームをやり直す。
- 同時ビンゴが76人以上の場合は、番号の**重複を許す**（全員に重複なしで振れないため）。同じ番号の人は距離が必ず同じになるので、手順4の再戦で処理される。
- 順位決定ゲームの間、本抽選は**一時停止**する。

### ゲーム終了
- 次のいずれかで終了する:
  - ホストが「ゲーム終了」を押す
  - 全員の順位が確定する
- 景品の数が設定されている場合、最後の景品が確定した時点で「ゲームを終了しますか？」というダイアログをホストに表示する。
